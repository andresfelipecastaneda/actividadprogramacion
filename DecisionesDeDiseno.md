| Decisión de diseño | Alternativas descartadas | Opción elegida | Justificación detallada |
|---------------------|--------------------------|----------------|--------------------------|
| Creación de clase base Persona | Definir atributos separados en cada clase hija | Crear clase abstracta `Persona` con atributos comunes | Se descartó la alternativa porque generaría duplicación de código y dificultaría el mantenimiento. La clase abstracta permite reutilizar atributos comunes y obliga a las clases hijas a implementar su propia actividad principal. Para la actividad se usó la inteligencia artificial como apoyo, lo que permitió comprender mejor este concepto. |
| Clases hijas (Estudiante, Docente, Administrativo) | Usar una sola clase genérica | Definir clases específicas que heredan de `Persona` | Se descartó la clase genérica porque no permitiría diferenciar atributos y comportamientos propios de cada rol. Con clases hijas se logra especialización: el estudiante tiene semestre y programa, el docente tiene tipo de contratación y horas, y el administrativo tiene cargo y experiencia. Cada uno implementa `realizar_actividad_principal()` de forma distinta. Para la actividad se usó la inteligencia artificial como apoyo, lo que permitió comprender mejor la herencia y el polimorfismo. |
| Programas y Asignaturas | Manejar asignaturas como texto plano | Crear clases `ProgramaAcademico` y `Asignatura` | Se descartó la alternativa porque no permitía validar ni relacionar datos. Con clases específicas se logra mayor integridad y flexibilidad. Para la actividad se usó la inteligencia artificial como apoyo, lo que permitió comprender mejor cómo modelar relaciones entre objetos. |
| Grupos Académicos | Relacionar estudiantes directamente con asignaturas | Crear clase `GrupoAcademico` con código, docente, horario y cupo | Se descartó la alternativa porque no reflejaba el proceso real de matrícula. Con la clase `GrupoAcademico` se logra representar mejor la inscripción y aplicar reglas de cupo. Para la actividad se usó la inteligencia artificial como apoyo, lo que permitió comprender mejor la composición de clases. |
| Horarios | Representar horarios como cadenas de texto | Crear clase `Horario` con atributos y métodos | Se descartó la alternativa porque no aseguraba integridad. Con la clase `Horario` se logra flexibilidad y consistencia en la gestión de horarios. Para la actividad se usó la inteligencia artificial como apoyo, lo que permitió comprender mejor la importancia de encapsular datos. |
| Manejo de errores | Usar solo excepciones genéricas de Python | Definir excepciones personalizadas (`GrupoLlenoError`, `EstudianteYaMatriculadoError`, etc.) | Se descartó la alternativa porque no diferenciaba situaciones específicas. Con excepciones personalizadas se logra claridad y control en los errores. Para la actividad se usó la inteligencia artificial como apoyo, lo que permitió comprender mejor el manejo de excepciones. |
| Validaciones de datos | Permitir valores vacíos o inválidos | Implementar setters y validaciones en atributos | Se descartó la alternativa porque afectaría la consistencia del sistema. Con validaciones se asegura integridad de la información. Para la actividad se usó la inteligencia artificial como apoyo, lo que permitió comprender mejor las validaciones y su aplicación en POO. |
